ProtoSim Help

Simulate industrial devices that real protocol clients (SCADA, HMI, PLC programs) can connect to.

Overview

ProtoSim runs one or more simulated devices (servers, slaves, outstations or brokers) on your PC. Each device speaks one protocol, listens on its own port and exposes tags: named, typed values mapped onto protocol addresses. Tags can hold fixed values or be driven by a simulation such as a sine wave or a counter.

Mix protocols

Modbus TCP and RTU, OPC UA, MQTT, Sparkplug B, DNP3, BACnet/IP, SNMP, MTConnect, REST API and scripted devices can run side by side in one project.

See the traffic

Every request and response is logged with a decoded summary, plus statistics and connected clients.

Break things on purpose

Fault injection adds delays, timeouts, error replies and dropped connections.

Quick start

  1. Choose Simulation › Add device (or the Add button above the device list) and pick a protocol. The new device comes with sample tags.
  2. Click Start on the device, or press F5 to start all devices.
  3. Tick Enable simulated values at the top left so simulated tags start changing.
  4. Point your client at the endpoint shown under the device name (for example 0.0.0.0:502).
  5. Save the project with Ctrl+S.
Ports below 1024 (such as Modbus 502) may already be used by another program. If a device shows Faulted, stop it, change the port on the Settings tab and start it again.

The main window

  • Enable simulated values — the master switch for simulation. When off, every tag keeps its current value.
  • Simulated devices — the list on the left. The dot shows the state: green running, amber starting/stopping, red faulted, grey stopped. Start all, Stop all and the delete button are below the list.
  • Clients — below the devices: sessions that connect to external servers and devices (see Clients). Green while connected or polling, red after a failed request.
  • Network links — below the clients: links made with the network wizard that feed tags here from other simulators (see Simulation network). Green while running, red after a failed cycle.
  • The Simulated devices list is always shown. Hide or show the Clients and Network links lists with View › Clients panel and View › Network links panel; the other lists take the space. Hide or show the whole left panel with the arrow button in the middle of the divider, or Ctrl+B. These choices and the panel's width are remembered.
  • Device pane — the selected device. Click its name to rename it. The tabs are described below.
  • Status bar — devices running, open connections, request rate and whether simulation is on.

Data tab Modbus · DNP3

Shows the raw memory of register- and point-based protocols, one area at a time (for example Holding Registers). Node- and topic-based protocols (OPC UA, MQTT) have no Data tab.

  • Choose the area, the Start offset and the number of Rows; page with the arrow buttons.
  • Format shows word values as unsigned, signed, hex, binary or ASCII.
  • Double-click a value to edit it. Bit areas have a check box per row.
  • Fill, Clear, Randomize and Sequence act on the visible rows.
  • Rows whose value just changed are highlighted.

Tags & simulation

Each row is a tag. Use Add tag, Duplicate and Remove above the grid. Shift+click selects a range of tags and Ctrl+click adds or removes single tags; Remove, Delete or right-click > Delete removes every selected tag (after asking, when there is more than one). The address formats for the device's protocol are shown above the grid.

Import & export CSV

Export CSV… saves the device's tags so you can edit them in a spreadsheet. Import CSV… reads them back.

When the device already has tags, the import asks what to do with them:

  • Append — keep the existing tags and add the imported ones after them.
  • Overwrite — remove all existing tags and replace them with the imported ones.

Columns

Name, Address, DataType, WordOrder, Simulate, Simulation, Min, Max, PeriodSeconds, Step, IntervalMs, Writeable, Description

Only Name and Address are required; column order doesn't matter and names are case-insensitive. Numbers use a dot as the decimal separator. Missing values get defaults (UInt16, ABCD, simulation off, Sine, 0–100, 10 s, step 1, 500 ms).

Logic designer

Choose Logic > Logic designer (Ctrl+L) to build function block programs that tie devices together, so several simulators behave like one plant. For example, a tank level on a Modbus device can start a pump whose run feedback is an OPC UA tag, while a BACnet setpoint feeds a PID loop.

Arranging the designer. Each block group (Tags, Logic, Compare, Math, Timers, Process) and Project tags is a collapsible panel beside the canvas. Click a panel's title to open or close it, drag the divider to resize the column, and use Panels to hide or show individual panels. Options > Restore panels brings them all back, and Options > Undock designer moves the designer to its own window. These choices are remembered.

Building a program

  • Add blocks by dragging them from the palette onto the canvas. Under Project tags, every tag of every device is listed as Device/Tag: drop one to get a Tag in block, or hold Ctrl while dropping to get a Tag out block.
  • Wire by dragging from an output (right edge) to an input (left edge), or the other way round. An input takes one wire; a new wire replaces the old one.
  • Move a block by dragging its header (it snaps to the grid). Click a block or wire to select it and edit its parameters on the right; Delete removes the selection. Ctrl + mouse wheel zooms.
  • Unwired inputs use a default (AND inputs count as true, OR inputs as false) or, where the block has one, the parameter of the same name, such as the compare blocks' B and the timers' PT.

Running

Run starts every enabled program, each on its own Scan interval (100 ms by default). Blocks are evaluated in data-flow order. Loops are allowed: a block fed by its own output sees the previous scan's value, so a pump that drains a tank whose level controls the pump just works. While running, every port shows its value, wires carrying true turn green, values appear in the block headers, and blocks with a problem (unknown tag, bad parameter) are outlined in red with the reason in a tooltip. Edits apply straight away, and timers, counters and latches keep their state. Tags written by Tag out blocks stop simulating while the logic runs and resume when it stops. Bool signals are 1 and 0, and numbers flow as decimals and are converted to each tag's data type when written.

Programs are saved with the project, and Run when the project opens starts them automatically. Tag references use device and tag names, so renaming a device or tag means updating the blocks that use it.

Record & replay

On the Tags & simulation tab, Record samples every tag (every 100 ms by default) and keeps each change, whether it came from simulation, a client's write or your edit. Stop & save… writes the recording to a CSV file:

# ProtoSim recording, started 2026-11-17T09:00:00.0000000Z
offset_s,tag,value
0,Tank level,42.5
0.25,Tank level,43.1
3.5,Pump running,true

Replay… plays such a file back into the tags at the chosen speed (0.25× to 60×), optionally looping. Recorded names are matched to tags by name, then by address, and you're told about any that don't exist. While replaying, those tags' simulation pauses; it resumes when the replay ends or is stopped. The first column can also hold timestamps instead of offsets (2026-03-01T08:00:30Z,Flow,12.5), so data exported from a historian or a real device can be replayed as-is.

Scenario scripts

The Scenario tab holds a timed script for the device, saved with the project. Each line is <time> <action>; # starts a comment. Times are seconds or durations such as 500ms, 30s, 1m30s or 2h, and a leading + makes a time relative to the previous step.

ActionEffect
set Pump running = trueWrites a tag (names with spaces are fine)
ramp Tank level from 20 to 80 over 30sMoves a numeric tag linearly; without from it starts at the current value
simulate Tank level on / offHands a tag back to its simulation, or holds it at its value
fault error 50 code 4, fault drop 20, fault delay 200 jitter 50, fault disconnect 10, fault clearChanges the device's fault injection
device stop / device startTakes the simulated device offline and back
log Pump tripsWrites a line to the Traffic log
repeat (last line)Starts again from the beginning

Run scenario checks the script first and points at any bad line or unknown tag. While it runs, the tags it sets or ramps pause their simulation, every step is logged on the Traffic tab, and the status shows the time, speed and current step. When it ends or you stop it, held tags go back to their simulation and fault settings return to what they were before the run. Insert example replaces the script with an annotated example.

Traffic

A live log of received (Rx) and sent (Tx) messages with decoded summaries; Modbus also shows the raw bytes in hex. Use Capture to stop or resume recording (saves CPU under heavy load), Frames and Events to choose what is shown, Auto-scroll to follow new entries, and Clear to empty the log. Filter matches the summary, remote address or hex bytes. The log can be exported to .log or .csv.

Connections

Counters for active and total connections, requests per second, requests, responses, exceptions sent, unanswered requests, malformed frames and bytes in/out. Reset counters sets them back to zero. The table lists each connected client or session; Disconnect drops it.

Settings

Protocol settings such as bind address and port. Settings can only be changed while the device is stopped. Tick Start this device automatically when the project is opened to have it start on load.

Fault injection

Makes a device misbehave so you can test how clients cope. Changes apply immediately, even while the device is running.

Modbus TCP

A Modbus TCP server (slave), default port 502. Supported function codes: 01–06, 08 (Return Query Data), 15, 16, 22, 23 and 43/14 (Device Identification).

Tag addresses

ExampleMeaning
HR:0 IR:0 CO:0 DI:0Holding register, input register, coil, discrete input — 0-based offsets.
40001 / 400001Modicon-style, 1-based (4x = holding, 3x = input, 1x = discrete input, 0x = coil).
HR:10.3Bit 3 of holding register 10.

Word order

32- and 64-bit values span several registers. ABCD is big-endian (the Modbus norm), CDAB swaps words, BADC swaps bytes in each word, and DCBA is little-endian.

Settings

Unit IDs to answer (*, 1,2,10-20), gateway exceptions for other unit IDs, unit 0 as broadcast, read-only mode, area sizes and device identification strings.

Modbus RTU serial · over TCP

Two more Modbus devices use the same function codes, memory tables, tag addresses, word orders and settings as Modbus TCP, but RTU framing: unit address, PDU and CRC-16, with no MBAP header.

  • Modbus RTU (serial) is a slave on a COM port. Its defaults are 19200 baud, 8 data bits, even parity and 1 stop bit, unit 1. A pause of 3.5 character times ends a frame; Frame gap can set it by hand. Turnaround delay waits before replying, for RS-485 masters. Several devices can share one port name as long as only one runs at a time. To test without hardware, create a virtual COM port pair (for example with com0com) and connect the master to the other end.
  • Modbus RTU over TCP accepts TCP connections that carry raw RTU frames, like a serial device server, default port 502. Known function codes are framed by their length; for others, a pause of Frame gap ends the frame.

As on a real RTU line, frames with a bad CRC are ignored, requests for other unit IDs get no reply (unless a gateway exception is chosen), and unit 0 is a broadcast that is processed but never answered. Injected errors are Modbus exceptions with a valid CRC. The serial device lists its port on the Connections tab; there is no connection to drop.

OPC UA

An OPC UA server (opc.tcp), default port 4840.

Tag addresses

A path whose levels are separated by . or /, such as BOB.MARY.SUE.PV or Plant/Tank1/Level. Each level is a folder, so BOB.MARY.SUE.PV browses as Objects > BOB > MARY > SUE > PV with the NodeId as typed, ns=2;s=BOB.MARY.SUE.PV. Set Root folder in the settings to put every tag under one folder instead. Folders are created automatically and nodes appear and disappear live as tags are added or removed.

Security

None, Basic256Sha256 Sign, or Sign & Encrypt; anonymous and/or user-name login. A self-signed certificate is created on first start in %LocalAppData%\ProtoSim\pki. Untrusted client certificates can be accepted automatically.

MQTT

A built-in MQTT broker, default port 1883. Each tag is a topic, for example sensors/temperature or plant/pump/running. Simulated values are published to the topic; external clients can publish and subscribe as with any broker. Anonymous access can be turned off and a user name and password required.

DNP3

A DNP3 TCP outstation, default port 20000, outstation address 10 and master address 1.

AddressPoint type
BI:<index>Binary input
AI:<index>Analog input
C:<index>Counter

Settings include the outstation and master addresses, unsolicited responses, whether writes are allowed, and the maximum number of points.

BACnet/IP

A BACnet/IP device on UDP port 47808 (0xBAC0), device instance 1001 by default. Leave Local IP address empty to choose the network interface automatically. On a PC with several interfaces (VPN, Hyper-V, WSL…) the start error lists them, so enter the one your BACnet network uses. Use 127.0.0.1 to test with a client on the same PC.

Add /name to set the Object_Name, for example AV:3/Zone Setpoint. Otherwise objects are named like Analog Value 3.

Services

  • Who-Is / I-Am and Who-Has / I-Have. I-Am is broadcast and, with Unicast I-Am replies on, also sent straight back to the requester.
  • ReadProperty and ReadPropertyMultiple (including ALL, REQUIRED and OPTIONAL) for the device object (Object_List, vendor and model information, protocol services and object types supported, local date and time…) and every object.
  • WriteProperty and WritePropertyMultiple. Outputs and values are commandable: writes go into the 16-level Priority_Array, the highest priority wins, writing NULL relinquishes that level, and the Relinquish_Default applies when every level is empty. Inputs are read-only until Out_Of_Service is set to true.
  • SubscribeCOV and SubscribeCOVProperty, confirmed or unconfirmed, with lifetimes. Analog objects notify when the value moves by at least COV increment.
  • DeviceCommunicationControl (disable silences everything except DCC and ReinitializeDevice), ReinitializeDevice (a cold start clears priority arrays) and TimeSynchronization. Set a Password to require one.

Errors use the standard BACnet classes and codes, such as unknown-object, unknown-property, write-access-denied, value-out-of-range and invalid-data-type. Injected errors are sent as error class DEVICE with the fault error code as the BACnet error code (for example 25, operational-problem). UDP has no connections, so the Connections tab lists clients heard from in the last 10 minutes. Drop forgets a client and cancels its COV subscriptions.

Simulated tags keep writing their values, so a simulated output overrides what a client commanded. Turn off simulation for points that clients should control.

SNMP agent

An SNMPv1/v2c agent on UDP port 161, for simulating UPSs, PDUs, switches and other monitored equipment. If the Windows SNMP service is installed it may already use 161; choose another port such as 1161 and point the manager at it. SNMPv3 requests are ignored.

Tag addresses

Each tag is one scalar object, addressed by its numeric OID, usually ending in .0, for example 1.3.6.1.4.1.99999.1.1.0. Add :syntax to choose the SNMP type:

The system group (1.3.6.1.2.1.1: sysDescr, sysObjectID, sysUpTime, sysContact, sysName, sysLocation, sysServices) is built in and set in the server settings.

Requests

  • Get: missing objects return noSuchObject or noSuchInstance in v2c, and a noSuchName error in v1.
  • GetNext and GetBulk (v2c) walk all objects in numeric OID order, ending with endOfMibView. Max GetBulk varbinds caps the size of one response.
  • Set needs the Write community. It is atomic: every variable is checked (exists, writable, right type, valid value) before any is changed. The system group is read-only.
  • Requests with an unknown community, or for a disabled version, get no reply, as with a real agent.

Traps

List Trap receivers (host or host:port, default port 162) to send SNMPv2c traps: coldStart when the agent starts and, with Trap on Set, a trap carrying the new values after each successful Set. That trap's snmpTrapOID is the sysObjectID followed by .0.1.

Injected error responses carry the fault error code as the SNMP error status (for example 5, genErr). The Connections tab lists managers heard from in the last 10 minutes.

MTConnect

An MTConnect agent for a simulated machine tool, serving XML over HTTP on port 5000. With the default device name Mill, try http://localhost:5000/probe and http://localhost:5000/Mill/current.

Tag addresses

Each tag is one data item: a component path, the data item id and its type, separated by :.

AddressMeaning
Axes/Linear[X]/Xact:POSITION.ACTUALSample Xact, type POSITION, subtype ACTUAL, in the Linear axis named X under Axes. Units default to MILLIMETER.
Controller/Path/execution:EXECUTIONEvent (String: ACTIVE, READY, STOPPED…)
Controller/system:SYSTEMCondition (String NORMAL / WARNING / FAULT, Bool true = FAULT, or 0/1/2)
partcount:PART_COUNTA data item on the device itself
Systems/flag:MY_FLAG:EVENTAny type, with the category given explicitly

Components are MTConnect element types (Axes, Controller, Path, Linear, Rotary, Systems, Electric, Coolant, Door…), optionally with a [name]. Common types know their category and units: samples such as POSITION, TEMPERATURE, ROTARY_VELOCITY and LOAD need numeric tags; events such as EXECUTION, CONTROLLER_MODE, PROGRAM and PART_COUNT take any type; conditions such as SYSTEM and HARDWARE map to Normal/Warning/Fault. Bool events become words where MTConnect expects them: EMERGENCY_STOP is ARMED/TRIGGERED, DOOR_STATE is OPEN/CLOSED, and other Bool events are ON/OFF. Data item ids must be unique; avail is the built-in AVAILABILITY event, which reads AVAILABLE while the agent runs.

Requests

RequestReturns
/probe or /MillMTConnectDevices: the device, its components and data items

Every request can be prefixed with the device name (/Mill/current) and filtered with path, an XPath over the probe document such as //Axes or //DataItem[@category="CONDITION"]. Each value change adds a numbered observation to a circular buffer of Buffer size entries; unchanged values are skipped unless Record unchanged values is on. A restart gives a new instanceId and starts the sequence again.

Errors come back as MTConnectError documents: NO_DEVICE (404), OUT_OF_RANGE, INVALID_XPATH, INVALID_REQUEST and UNSUPPORTED (400), and INTERNAL_ERROR (500, used for injected errors). Streaming with interval isn't supported; clients poll current or sample instead.

JSON

Responses are XML unless the client asks for JSON with Accept: application/json or ?format=json (?format=xml forces XML). Default format sets what plain requests get. The JSON follows the reference agent's JSON version 2 layout: each document is an object named after its root (MTConnectStreams…) with jsonVersion and schemaVersion; attributes become properties, element text becomes value (a number for samples), containers such as Header, Devices, DataItems and Samples are objects, and repeating elements are arrays grouped by name, for example Streams.DeviceStream[0].ComponentStream[n].Samples.Position[0].value. Errors come back as JSON too.

Scripted device

A device that answers text requests with replies you define. Use it for instruments (SCPI-style), scales, barcode readers, test fixtures and other ASCII protocols that have no plugin of their own. Choose the Transport: a TCP server (default port 10001), a UDP endpoint, or a serial port.

Rules

The Rules setting holds one rule per line, request => reply, checked from the top; the first match answers. Lines starting with # are comments.

In the requestMeaning

In the replyMeaning

An empty reply stays silent. Requests that match no rule get the Unknown command reply (empty to stay silent). Each tag's address is just the variable name the rules use, such as Temperature.

Framing and output

Request framing decides where a request ends: any newline (default), CR, LF, CRLF, a Custom terminator such as \x03, or Silence (a pause of Frame gap). Over UDP each datagram is a request, or several if it holds several lines. Reply terminator (default \r\n) is added to every reply, and Echo requests sends each request back first. For unsolicited output, Greeting is sent when a TCP client connects, and Periodic message is sent every Period to all TCP clients, recent UDP senders, or the serial port, for example a scale streaming ST,GS,{Weight:+0000.00}kg.

Rule errors stop the device from starting and name the bad line. Injected errors send the Error reply with {code} set to the fault error code.

REST API

A JSON-over-HTTP API simulator. It listens only on this computer's loopback interface (127.0.0.1 and ::1), so other machines can't reach it. The base URL is built from the Host name, TCP port and Base path settings, default http://localhost:5080/api/v1. Every response is JSON (application/json; charset=utf-8).

Authentication

With Require bearer token on (the default), each request needs Authorization: Bearer <token>. Tokens come from the OAuth 2.0 client credentials endpoint, default http://localhost:5080/oauth/token:

curl -X POST http://localhost:5080/oauth/token -d "grant_type=client_credentials&client_id=protosim-client&client_secret=..."

Credentials can be sent as form fields, as JSON, or as HTTP Basic. The response holds access_token (an HS256-signed JWT), token_type and expires_in. On the API clients tab you add clients, each with its own client ID, secret and optional scopes; disable a client or generate a new secret; get a token for testing; and revoke all tokens. Tokens are kept while ProtoSim runs and end when it closes.

Simulated GET endpoints (tags)

Each tag's address is a path relative to the base URL. The tag sensors/temperature answers GET /api/v1/sensors/temperature with {"path", "value", "dataType", "timestamp"}, or just the value when Tag response format is ValueOnly. Tags are simulated like any other protocol. PUT, PATCH or POST to a tag path writes its value (42, true, "text" or {"value": 42}). GET /api/v1/_tags lists all tags and GET /api/v1 describes the API.

JSON database

Paths that aren't tags go to a JSON database. Each device creates its database once, filled with sample data, in %LocalAppData%\ProtoSim\RestDatabases, and keeps it across restarts. Every change made through the API is saved straight away. Each top-level property is a resource:

On the Database tab you can edit the whole database as JSON and apply it, Recreate it from the sample data, and Export it to a file and Import that file on another computer. The project file stores which database a device uses but not its contents, so export the database to move it with a project.

Errors and faults

Errors are JSON: {"error", "message", "status"} (token errors use the OAuth error/error_description format). Injected error responses map the fault error code to an HTTP status: 1 → 405, 2 → 404, 3 → 400, 6 → 503, anything else → 500. A dropped response closes the connection without answering. CORS headers are added unless Allow CORS is off.

Sparkplug B

A simulated Sparkplug B (spBv1.0) edge node. With Broker set to Embedded (the default), ProtoSim also runs an MQTT broker on the Embedded broker port (default 1883) and the edge node connects to it. Set it to External to publish to another broker, such as Mosquitto, HiveMQ or Ignition's MQTT Distributor.

Data types map to Sparkplug types: Bool → Boolean, Int16/32/64, UInt16/32/64, Float32 → Float, Float64 → Double, String. bdSeq and Node Control/... are reserved.

Behaviour

  • On connect the edge node registers NDEATH (with bdSeq) as its MQTT will, then publishes NBIRTH and one DBIRTH per device. Each new MQTT session increments bdSeq.
  • Changed values are reported by exception: changes are collected for Publish interval and sent in one NDATA or DDATA per device, with seq counting 0–255.
  • With Use aliases on, births carry names and aliases and data messages carry only aliases.
  • NCMD and DCMD write metric values (by name or alias). Node Control/Rebirth = true republishes all births. Adding or removing tags while running also triggers a rebirth; a device whose last metric is removed gets a DDEATH.
  • With a Primary host ID, births wait until spBv1.0/STATE/<host> (or the older STATE/<host>) reports online, and NDEATH is sent when the host goes offline.
  • Stopping the device publishes NDEATH and disconnects cleanly. Drop on the Connections tab closes the session without DISCONNECT, so the broker publishes the will.

Faults

Response delay and jitter delay data messages, Drop responses skips data messages, and Disconnect after response drops the MQTT session after a data message (the edge node reconnects after Reconnect delay). Error responses don't apply.

Clients

A client connects to an external server or device, real or simulated, and pulls its data in. Add one with Simulation > Add client or the Add button above the Clients list.

  • Connection — host, port and protocol options. Disconnect to change them.
  • Request — what to send. Send once runs it; Poll repeats it every Poll every ms until Stop. Tick Start polling when the project opens to poll automatically.
  • Results — one row per value: its address, the raw representation and the decoded value. Successes, failures and the response time are shown above, and the traffic log below.
  • Copy into tags — select a result row and click Map selected row (or Map all rows), then pick a project tag as Device/Tag. After every successful request each mapped value is written into its tag, so a simulated server re-publishes it and logic programs can use it. Mapped tags pause their own simulation while the client polls. Last copy shows what was written or why it couldn't be.

Simulation network

Simulators can talk to each other the way controllers in a real plant do: a line PLC reads a tank's level from an OPC UA server, a SCADA node reads several PLCs, a BMS writes a setpoint back. The simulators can be devices in one ProtoSim, or in ProtoSim instances on other computers (for example one per Raspberry Pi or per PC on the plant network).

A network link is a protocol client that polls points on a source device and copies them into tags of a device in this project. It speaks the source's own protocol, so the traffic is real and shows in both devices' traffic logs.

The network wizard

Open it with Network › Network wizard…, the Wizard button above Network links, or Ctrl+Shift+W.

  1. Source — pick a device in this project, a device in ProtoSim on another computer, or any server or real device.
    • Another computer: the wizard searches the local network and lists every ProtoSim instance that shares its devices, with their devices and tags. Computers on another subnet don't hear the search; type their names or IP addresses in Also ask.
    • Any server: pick the protocol, fill in the connection settings, and type the addresses on the next page.
  2. Values — tick the tags to bring over. Read copies the source value into the tag here. Read + write also sends changes made here (by a client, logic, a scenario or simulation) back to the source; the source tag must be Writeable, and inputs (DNP3, BACnet inputs, Modbus input registers and discrete inputs, MTConnect) can only be read.
  3. Target — pick the device that receives the values. Create new tags adds a tag per value with a free address the wizard suggests (you can change it), named after the source tag; or copy into tags that already exist. Each target is checked before you continue.
  4. Finish — name the link, set the poll interval, and start it (and the source device, if it is stopped).

The link page

Select a link under Network links to see every point with its last value and status, the cycle count, failures and write-backs, and the client's traffic. Start and stop it, edit the connection while stopped, change directions, add or remove points, and choose whether it starts when the project opens. Read-only points pause their tag's own simulation while the link runs. Links are saved with the project.

Sharing devices with other computers

Network › Share devices on the network (on by default) lets wizards on other computers find this ProtoSim. It answers searches on UDP port 47900 and serves the list of devices and tags on a TCP port of its own. Windows Firewall may ask to allow ProtoSim the first time; allow it on private networks. Turn sharing off on networks you don't trust: other computers can then no longer find this instance (its devices still answer clients that know their addresses).

The device list includes each device's connection settings, including any user names, passwords and community strings that clients need, so that a link on another computer can connect. REST API devices only listen on this computer, so they are not shared. BACnet/IP devices on computers with several network adapters need Local IP address set in their settings.

Project files

Projects are saved as .psim files (JSON). A project holds the devices, their settings, fault settings, tags and values, raw Modbus memory, client sessions with their tag mappings, network links, and logic programs. To open a project at startup, pass its path on the command line: ProtoSim.exe project.psim.

Projects from earlier versions open unchanged. Tags that use the None simulation kind keep their value, and tags saved before the Writeable column existed are not writeable.

Each protocol is a plugin. To add a protocol, copy its DLL into the Plugins folder next to ProtoSim.exe and restart. Help › About ProtoSim lists the installed protocols and any plugins that failed to load.

What's new in 1.3

  • ProtoSim now runs on Windows, macOS and Linux, with a new cross-platform interface. On macOS, shortcuts use Command instead of Ctrl. Ports below 1024 (such as Modbus 502) may need extra rights on Linux and macOS, so use a higher port there.
  • Network wizard connects simulators into a simulation network, in one ProtoSim or across computers: pick a source device, the values, and the device that receives them (see Simulation network).

  • ProtoSim instances find each other on the local network (Network › Share devices on the network).

  • DNP3 outstations now send updated values to masters while running (before, masters only saw the values from when the device started), and floating-point analog inputs are no longer rounded.
